# Журнал VPS · Proxy Tunnel 0.1.8

Пакет подготовлен для отдельного согласования. На VPS ничего не установлено. Установка не запускается из Windows-приложения.

## Что будет добавлено

Отдельная служба `proxy-tunnel-observer.service`. Примерно каждые 5 секунд она сохраняет CPU, steal/iowait, нагрузку, доступную память/swap, свободное место, общие TCP-счётчики, состояние и перезапуски службы туннеля, наличие TCP-порта транспорта. Из существующего журнала копируются события только `proxy-tunnel-prototype.service`; курсор сохраняется после записи истории. Раз в минуту выполняются два коротких HTTPS-запроса к Cloudflare и AWS для проверки исходящей связи. HTTP-ошибка тоже показывает, что узел достижим. При остановке ОС/наблюдателя история отсутствует; программа не может записывать данные в это время.

История хранится в `/var/lib/proxy-tunnel-observer`: до 14 дней или примерно 200 МБ, что наступит раньше, сегменты примерно по 4 МБ. Запись может немного превысить предел до очередной ротации. Службе назначены лимиты CPU 5%, памяти 64 МБ и 16 задач; это ограничения, а не обещание нулевой нагрузки. Если память исчерпана, systemd может перезапустить наблюдатель. На маленьком VPS влияние следует проверить после согласованной установки.

Служба не открывает входящих портов, не меняет маршруты, DNS, firewall, SSH и настройки туннеля; службу туннеля не перезапускает. Используется отдельный временный пользователь systemd с правом чтения системного журнала. Программа выбирает только журнал нашей службы; само членство в группе systemd-journal даёт более широкое право чтения.

Файлы установки: `/opt/proxy-tunnel-observer/observer.py` и `/etc/systemd/system/proxy-tunnel-observer.service`. Зависимости: Linux, Python 3.9+, systemd 247+, штатные `journalctl`, `systemctl`, `ss`. Ubuntu 24.04 подходит по базовым требованиям. Дополнительные пакеты установщик не скачивает. Установка требует root. Данные с паролями известных форматов очищаются; содержимое трафика, окружение процессов и конфигурация с ключом не собираются. IP-адреса и технические сообщения в журнале остаются.

## Как Windows получает данные

По SSH с ранее подтверждённым ключом сервера. При включённом туннеле SSH идёт внутри него через SOCKS; отдельный доступ в обход kill switch не добавляется. При отсутствии связи запрос ждёт восстановления, а локальная часть отчёта остаётся доступна. Самостоятельно сервер ничего на ПК не отправляет. Время запроса и оценка разницы часов добавляются в отчёт; задержка запроса ограничивает точность сопоставления.

«Сервер → Получить логи VPS» показывает журнал службы и историю наблюдателя за выбранный период. «Журнал → Копировать логи» объединяет их с ПК. Автоматический отчёт о сбое использует 5 минут до и после события. Один экспорт истории ограничен примерно 1 МБ и явно сообщает об ограничении или повреждённых записях. ∞ означает всю сохранившуюся историю, а не восстановление удалённых записей. TCP-счётчики относятся ко всему VPS, а не к конкретному пользователю. Сопоставление помогает локализовать причину, но само по себе не доказывает место потери пакетов.

## Установка только после отдельного подтверждения

Распаковать весь пакет в отдельный каталог VPS. Три скрипта и SHA256SUMS должны лежать рядом. Для текущего порта транспорта:

```sh
sudo /usr/bin/python3 -I install.py --port 24443
systemctl status proxy-tunnel-observer.service --no-pager
sudo /usr/bin/python3 -I /opt/proxy-tunnel-observer/observer.py --export --bytes 16384
```

Установщик проверяет SHA256, отказывается заменять неизвестные файлы, при ошибке пытается вернуть прежние файлы и состояние только наблюдателя. После установки нужно проверить реальные метрики, чтение журнала, ограничения ресурсов и получение отчёта из Windows. Эти проверки на рабочем VPS ещё не выполнялись. Linux/systemd проверены только подставными тестами команд и файлов; установка на реальной Linux-машине пока не испытана.

## Остановка и удаление

```sh
sudo systemctl stop proxy-tunnel-observer.service
sudo /usr/bin/python3 -I uninstall.py
```

Для удаления нужен исходный пакет с корректным SHA256SUMS. Удаляются только служба и скрипт наблюдателя, история сохраняется. Служба туннеля не затрагивается. Если наблюдатель перестал писать, посмотреть `journalctl -u proxy-tunnel-observer.service -n 50 --no-pager`; удалять историю для восстановления не требуется.
