# Обновления из GitHub Releases · 0.1.10

В настройках появилась кнопка «Проверить обновления». Она работает при подключённом полном туннеле и включённом kill switch. Источник закреплён: https://github.com/lonchdev/proxy-tunnel-desktop . GitHub-аккаунт или токен пользователю для публичных выпусков не нужен.

## Порядок

1. Получить последний стабильный Release через локальный прокси, принудительно направленный на VPS. Прямого запасного HTTP-подключения нет. Draft и prerelease пропускаются; равная/меньшая версия не устанавливается.
2. Скачать update.json и update.sig, проверить ECDSA P-256 / SHA-256 закреплённым открытым ключом из EXE. Затем показать версию и текст изменений и спросить пользователя об установке.
3. Скачать архив через VPS (до 256 МБ / до 15 минут), проверить подписанные размер, SHA256 архива и SHA256 EXE. В ZIP допускается ровно один файл с фиксированным именем ProxyTunnel-Prototype.exe: все рабочие компоненты и интерфейс встроены в него. Персональные настройки вне папки приложения не заменяются.
4. Запустить отдельную проверенную копию текущего EXE как установщик. После его подтверждения включить блокировку установки и остановить туннель без обычного Disconnect/Disarm. В этом режиме разрешён только loopback; VPS, LAN, физические DNS и DHCP не разрешены. Это временно ограничивает и локальную сеть.
5. Дождаться завершения основного процесса, сохранить previous.exe и заменить EXE в прежней папке. Кратковременные файловые блокировки, в том числе процессом восстановления прокси, повторяются до 10 секунд. Долговременная ошибка оставляет защиту и прежний файл/резервную копию для восстановления.
6. Запустить новую версию. Для восстановления разрешить соединение с VPS на настроенном TCP/UDP-порту и работу TUN, сохраняя запрет физического прямого интернета. После двух проверок выхода и проверки общего маршрута Windows вернуться к обычному kill switch и отметить обновление завершённым. Проверка аккаунтов внешних сервисов не является частью подтверждения маршрута.

Настройки и SSH-ключи хранятся отдельно и сохраняются. Версия 0.1.9 не содержит установщика: переход на 0.1.10 выполняется вручную. Последующие обновления требуют публикации подписанного Release с большим номером. Пока такого выпуска нет, кнопка сообщает об отсутствии новой версии.

## Ошибка и восстановление

Повреждение подписи/архива отклоняется до блокировки и замены. Отмена загрузки не меняет установленные файлы и защиту. После начала замены отмена не предлагается.

Если новый процесс не запустился или завершился до подтверждения туннеля, установщик пытается вернуть проверенную резервную копию и запустить её с сохранённой защитой. Если программа работает, но VPS недоступен, через 3 минуты установщик прекращает ожидание, не снимая блокировку и не объявляя версию сломанной. Можно повторить подключение или нажать «Вернуть прежнюю версию» на странице настроек. Ручной откат доступен после завершения первой проверки установщиком. Ошибка отката также не снимает защиту.

Маркер незавершённого обновления хранится в каталоге данных приложения `updates/pending.json`. Обычный выход при таком маркере сохраняет блокировку. Перезапуск приложения из прежней папки повторяет восстановление. При отсутствии физической сети оно ждёт её появления; DHCP в строгом режиме установки запрещён, поэтому при утрате аренды сети может понадобиться ручное восстановление. Намеренное аварийное отключение защиты возможно существующей командой «Отключить kill switch.cmd» — это осознанно открывает обычный интернет и снимает маркер восстановления.

В `updates/<идентификатор>/` остаются резервная копия и данные транзакции. Автоматическая очистка этих резервных копий пока не реализована; на один выпуск нужно свободное место под архив и несколько копий EXE (желательно не менее 1 ГБ). Не удаляйте текущую транзакцию до завершения восстановления.

## Границы проверки

Проверены подписи, повреждение данных, состав ZIP, замена/откат файлов и временная блокировка файла на Windows. Политики установки и восстановления проверены моделью правил; сетевые регрессии — локальным тестовым каналом, без TUN/WFP. Реальная смена WFP-правил с продолжающимся трафиком, установка поверх запущенной пользовательской версии, сбой питания/перезагрузка и полный цикл обновления через GitHub на этой машине **не испытывались**. Эти испытания владелец ранее отложил; их нельзя считать пройденными. Механизм остаётся прототипом, обещания абсолютного отсутствия утечек до таких испытаний нет. WSL/виртуальные машины отдельно не подтверждены.

Смена правил выполняется в транзакции WFP. Microsoft описывает повторную проверку существующих ALE-потоков при изменении политики: https://learn.microsoft.com/en-us/windows/win32/fwp/ale-re-authorization . Это основание реализации, а не замена проверки на целевой Windows.

## Формат выпуска

Стабильный tag: `v0.1.10`, затем `v0.1.11` и т.д. Release содержит ровно по одному файлу с именами:

- `ProxyTunnel-update-win-x64.zip` — служебный архив только с EXE;
- `update.json` — Version, ArchiveSha256, ArchiveSize, ExeSha256;
- `update.sig` — 64 байта подписи P1363 над точными байтами JSON.

Дополнительно публикуется полная поставка с лицензиями и соответствующими исходниками компонентов. Минимальный ZIP предназначен для установщика и не заменяет полную поставку при выполнении условий распространения.

Изменение байтов JSON после подписи делает подпись недействительной. Закрытый ключ не находится в репозитории; публичный ключ `update-public-key.pem` должен входить в исходники и в EXE. Хеш файла из того же неподписанного источника сам по себе не подтверждает подлинность.

Сборка/подпись владельцем выполняется инструментом `release-tools/ReleaseSigner` из публичной копии. Параметры: `package EXE VERSION PRIVATE_KEY OUTPUT_FOLDER`, проверка: `verify OUTPUT_FOLDER PUBLIC_KEY`. Генерация новых ключей (`keygen PRIVATE_PATH PUBLIC_PATH`) не выполняется для каждого выпуска: прежние приложения доверяют уже закреплённому ключу. Закрытый ключ хранится отдельно с ограниченными правами; его резервную копию следует хранить вне публичного репозитория. Автоматическая ротация ключа пока не реализована.
